# 0006. 通知判定：サーバー側で行い、2 つのデータ源で重複させない

- ステータス: 採用
- 日付: 2026-11-19

## 背景

従来はローカルサーバーがメモリ上の前回状態と比べて「オフライン → LoL で在席」を検出していた。
SaaS 化では、エージェントの送信が途切れる、サーバーレスでメモリが残らない、Riot API という 2 つ目のデータ源が加わる、といった点を考える必要がある。

## 決定

- **判定はサーバー側**（`lib/core.js` の `applyPush`）で行う。エージェントは LCU の値から必要な項目だけを選んで送るだけにする。判定ロジックを 1 か所にまとめ、Discord 通知もサーバーから送れるようにするため。
- 前回状態（`prev`）と最後に通知した時刻（`notified`）は `u:<uid>:agent` に保存する。
- 判定ルールは従来と同じ。
  - LoL の在席は `availability` と `productId` / `gameStatus` で判定する（Riot クライアントのみ・他タイトル・モバイルは除く）。
  - 離席中などで一旦見送った相手は `pending` として覚えておき、ゲームに入った時点で通知する。
- 途切れの扱いは、送信の間隔で判断する。
  - エージェントは状態が変わらなくても 60 秒ごとに送る。
  - 前回の成功から `STALE_MS`（180 秒）以内なら前回状態を保持し、途切れていた間のオンライン化も通知する。
  - 180 秒を超えた場合と初回は、基準を取るだけで通知しない（通知が一斉に鳴るのを防ぐ）。
- **重複の防止**：再通知を抑える判定では、エージェントと Riot の `notified` の新しい方を使う。どちらの経路で通知しても、抑制時間内はもう一方から通知しない。
- 「LoL でオンラインのときだけ通知」の設定を切り替えたら、通知せずに基準を取り直す（`resyncPresence`）。
- 判定ロジックは `test/core.test.js` と `test/riot.test.js` でテストする。

## 結果

- 良い点：ブラウザを閉じていても Discord に通知できる。ローカル版と同じ取りこぼし対策を維持できる。
- 悪い点：エージェントの送信ごとにサーバー側で状態を読み書きする（Redis 2 コマンド）。
